# Phase 4: Obsidian graph + Plan tab: design

Status: draft for review · 2026-10-24
Builds on: phase 1 (views, notes, groom), phase 2 (board), phase 3 (theme), all on `main`.

Two parts, built in order: **4a: Obsidian-ready notes folder** (small, useful on its own, sets the link conventions) and **4b: the Plan tab** (larger, explicitly an experiment).

---

## Why

The user plans work for a newly forming team across three product areas. Jira is "not well formed": epics are per area, nothing ties them into team initiatives, and product's roadmap lives in Aha. The user wants to:

- **See groupings that lists hide.** Tables show one ticket per row; Jira shows one ticket's links at a time. A free-form graph (Obsidian) should surface clusters and orphans across tickets, notes and plans.
- **Map out an initiative as vertical slices.** Rather than each area building its horizontal layer and nothing working end-to-end until late, each sprint should deliver one or two thin, demoable client journeys (tracer bullets) cutting across areas, with explicit room for de-risking upcoming slices and for further-off exploratory work. The user defines this structure locally, links it to whatever Jira has, and uses it to drive backlog sorting and report to the team, who then tidy Jira to match.

Product owns each slice; the user supports execution and delivery.

The user is unsure how useful the Plan tab will be in practice; it is an experiment. It must be cheap to use (sketching a slice should take a minute, not an hour) and must not disturb the rest of the app.

## Goals

- 4a: Pointing Obsidian at `NOTES_DIR` gives a meaningful graph: tickets linked to their epic/parent, Jira issue links, the user's notes and groom files, and (after 4b) initiatives and slices. The user's own fields (categories, custom columns) are visible as properties and usable as tags.
- 4b: A **Plan** tab where the user can author and see one initiative at a time as a sprint × lane grid, with the flags described below.
- Everything authored is plain markdown/YAML in `NOTES_DIR`, so Claude (and Obsidian) can read and edit it; external edits show up live like notes do today.

## Non-goals

- Building a graph view inside the app (Obsidian provides it).
- Writing anything to Jira. Jira stays read-only (GET only).
- Aha integration.
- Export/reporting beyond a "Copy for Claude" of an initiative (reporting comes later).
- Story-point capacity planning; multiple initiatives on one grid; an Obsidian plugin.

## Anti-goals (would make this a failure even if it works)

- **Ceremony.** If mapping a sprint is slow or fiddly, it will be abandoned. Creating a slice, a step and attaching a ticket must each be a couple of keystrokes/clicks.
- **The app clobbering the user's writing.** The app only ever fully rewrites files it owns (`jira/tickets/`). For user-authored files it edits front matter and preserves the body, the same as notes today.
- **Noisy flags.** Flags are hints in muted colours, never errors or blockers.
- **Leaking real names into the shipped app.** Areas, stewards and owners come from config; examples and defaults are generic (Area A/B/C, Steward A, Product lead).

## Constraints (unchanged from earlier phases)

- Node ≥22.18 with native TS, no new runtime dependencies unless unavoidable (current: `yaml`, `marked`).
- Server bound to 127.0.0.1; existing Host/Origin/Content-Type gates and CSP apply to new routes.
- No network traffic except to Jira; token never logged.
- Tests must use temp `NOTES_DIR`s; never touch `~/atlassian-notes-data` or `~/.config/atlassian-notes`.
- Chrome only.

## 4a: Obsidian-ready notes folder

The vault is `NOTES_DIR` itself. Obsidian already ignores dot-folders, so `.cache/` stays out of the graph.

### Generated ticket files: `jira/tickets/KEY.md`

The app owns this folder. One file per ticket in the **union of all cached tickets** (every view's cache plus the board cache, and in 4b the plan caches). Files are written after each refresh, **only when content changed** (avoid churning Obsidian's index). Files for tickets no longer in any cache are deleted. The user is told (README, and a first line in each file) that edits here are overwritten.

Content:

```markdown
---
key: AAA-101
summary: Define builder step
status: Done
statusCategory: Done
type: Story
priority: Medium
assignee: Jane Doe
sprint: Sprint 12
labels: [foo]
url: https://…/browse/AAA-101
parent: "[[jira/tickets/AAA-12|AAA-12]]"
links:
  - "[[jira/tickets/AAA-110|AAA-110]]"
tags: [jira/story, category/tech-debt]
category: Tech debt          # user's custom column values, copied from the note
---
<!-- Generated by atlassian-notes from Jira; edits here are overwritten. -->
# AAA-101 · Define builder step

- Note: [[jira/notes/AAA-101|my note]]       (only if the note exists)
- Groom: [[jira/groom/AAA-101|groom]]        (only if the groom file exists)
- Blocks [[jira/tickets/AAA-110|AAA-110]]    (one line per Jira issue link, with its type/direction)
```

Decided:

- **Links use full vault paths** (`[[jira/tickets/KEY|KEY]]`) because notes, groom and ticket files all share the name `KEY.md`, so a bare `[[KEY]]` is ambiguous. Every link the app writes, in 4a and 4b, uses this form.
- **The ticket file is the hub.** It links out to the note and the groom file, so the user's note files need no changes.
- **Jira issue links** are newly fetched: add `issuelinks` to the search fields and extend `Ticket` with `links: { type: string; direction: "inward" | "outward"; key: string }[]` (type text as Jira phrases it, e.g. "blocks" / "is blocked by"). Shown in the ticket file; not added to the table UI in this phase.
- **Parent** is already fetched; it becomes the `parent` link. If the parent isn't in any cache, the link still resolves as an unresolved ("ghost") node in Obsidian, which is acceptable.
- **User fields → properties and tags.** Custom column values from the note's front matter are copied as properties; select-type values also become tags `<column-id>/<slugified value>`. Ticket type becomes `jira/<type>`.
- Watcher: `jira/tickets/` changes are ignored (app-owned; no live event).

Left to the builder: exact slug rules for tags, the order of properties, how deletion of stale files is batched.

### README: "Use with Obsidian"

A short section: open `NOTES_DIR` as a vault; suggested graph colour groups (`path:jira/tickets`, `path:jira/notes`, `path:plan`); note that `jira/tickets/` is generated. The app does not write `.obsidian/` config.

## 4b: Plan tab

### Concepts

| Term | Meaning |
|---|---|
| **Period** | A planning period, by default a quarter (e.g. `Q1 2027`). Configurable: a period is just a name plus its ordered list of sprints. |
| **Area** | A product area with a steward. Generic, configured in YAML. |
| **Initiative** | A team-level piece of work within a period (e.g. "Initiative 1 · Discovery → MVP"). Has an owner (product) and a set of Jira epics, each mapped to an area. |
| **Slice** (tracer bullet) | A thin, demoable client journey within **one sprint** of an initiative. Has a title, owner (product), delivery lead (default "me"), and ordered **steps**. Each step is one line of journey text, belongs to an area, and holds zero or more tickets. |
| **De-risk item** | Lane 2. A ticket (or an idea with no ticket yet) in a sprint that enables an upcoming slice. |
| **Path item** | Lane 3, "clear the path". Further-off, exploratory or product/design work: a ticket or an idea, with an optional free-text tag (`product`, `design`, `eng`, …). |

### Screen

Wireframe agreed in brainstorming (`.superpowers/brainstorm/…/plan-full.html`, not committed). In words:

- **Plan** is a fixed tab placed after the Kanban icon, before the view tabs.
- **Header:** period picker, initiative picker (plus "New initiative"), the initiative's owner and epics (edit), Refresh, and **Copy for Claude**.
- **Grid:** a row-header column, then one column per sprint of the period (in config order). Each column header shows the sprint name, its Jira state if known (active/future/closed), and a thin **lane-split bar** with ticket counts per lane (slice / de-risk / path).
- **Lane ① Vertical slice:** a slice header row (title in the slice's colour, owner, delivery, `done/total`, gap count), then **one row per area** (name + steward). In each sprint column a slice is a coloured vertical band; its steps sit in their area's row, numbered in journey order. A sprint column may hold one or two slices side by side (more is allowed and just gets narrow). Empty area cells show a muted "＋ step".
- **Lane ② De-risk the future:** per sprint, a list of items: ticket chip + summary, "→ slice" badge in that slice's colour, done tick.
- **Lane ③ Clear the path:** per sprint, a list of items with tag text; ideas shown with ✎.
- **Unplaced tray** below the grid, collapsed by default: tickets in the initiative's epics that are in no slice step and no lane item; drag a chip from the tray onto a step or lane.
- Clicking any ticket chip opens the existing ticket drawer (notes, groom, copy, ★ all work as today).
- Uses the current theme tokens and motion; works at the app's usual widths with horizontal scroll inside the grid if many sprints.

### Authoring interactions

All authoring is in the UI; each action is a small write to the relevant file.

- **New initiative:** dialog with title, period, owner, epics (keys) each with an area select.
- **New slice:** "＋ slice" in a sprint column's lane ① header → inline title input (Enter saves); owner/delivery editable on the slice header.
- **Add step:** click "＋ step" in an area cell → inline one-line input. Steps append to the slice in order; drag a step within its slice to reorder (renumbers). Edit text inline; delete via a small ×.
- **Attach ticket:** type a key into a step's inline "＋ key" input, or drag a chip from the tray or from another step/lane. Remove via ×.
- **Lane ②/③ items:** "＋ add" → input that accepts a ticket key *or* free text (free text = idea). Lane ② items then pick the slice they enable (select of the initiative's slices in **later** sprints, or none). Lane ③ items take an optional tag.
- **Notes:** initiative and slice markdown bodies are editable in a side drawer (same editor as ticket notes), e.g. for a demo script.
- Keyboard: Enter saves, Esc cancels, consistent with existing inline editors.

### Flags (muted hints, never blocking)

1. **Gap:** a step with no tickets → "no ticket".
2. **Not vertical:** all of a slice's steps are in one area.
3. **Spill:** a slice ticket whose Jira sprint is a later sprint than the slice's sprint.
4. **Enables nothing:** a lane ② item with no slice.
5. **Late de-risk:** a lane ② item not done (statusCategory ≠ Done) while its enabled slice's sprint is the active sprint or earlier.
6. **Progress:** slice header shows done/total tickets (statusCategory Done).

### Files (in `NOTES_DIR/plan/`)

```
plan/plan.yaml                       # periods, areas
plan/initiatives/<slug>.md           # one per initiative
plan/slices/<slug>.md                # one per slice
plan/sprints/<initiative>--<sprint-slug>.md   # lanes ② and ③ for one initiative × sprint
```

`plan/plan.yaml`:
```yaml
periods:
  - name: Q1 2027
    sprints: [Sprint 12, Sprint 13, Sprint 14, Sprint 15, Sprint 16, Sprint 17]
areas:
  - { id: a, name: Area A, steward: Steward A }
  - { id: b, name: Area B, steward: Steward B }
  - { id: c, name: Area C, steward: Steward C }
```
Sprint names are matched to Jira sprint names exactly; a configured sprint that Jira doesn't know yet is simply "future/local". This file is edited by hand (consistent with `views.yaml`/`columns.yaml` being config-in-files), except that the UI may append a new period when creating an initiative for a period that doesn't exist. If missing, the Plan tab shows a short empty state explaining how to create it, with a generic example.

`plan/initiatives/initiative-1.md`:
```markdown
---
title: Initiative 1 · Discovery → MVP
period: Q1 2027
owner: Product lead
epics:
  - { key: AAA-12, area: a, link: "[[jira/tickets/AAA-12|AAA-12]]" }
  - { key: BBB-40, area: b, link: "[[jira/tickets/BBB-40|BBB-40]]" }
---
Free notes…
```

`plan/slices/tb1-one-step-flow.md`:
```markdown
---
title: Create a 1-step flow, get notified
initiative: "[[plan/initiatives/initiative-1|Initiative 1]]"
sprint: Sprint 12
owner: Product lead
delivery: me
colour: 1            # index into a fixed theme-friendly palette; assigned on create
steps:
  - { area: a, text: define step, tickets: [AAA-101], links: ["[[jira/tickets/AAA-101|AAA-101]]"] }
  - { area: c, text: notify,      tickets: [CCC-31],  links: ["[[jira/tickets/CCC-31|CCC-31]]"] }
---
Demo script / notes…
```

`plan/sprints/initiative-1--sprint-12.md`:
```markdown
---
initiative: "[[plan/initiatives/initiative-1|Initiative 1]]"
sprint: Sprint 12
derisk:
  - { ticket: CCC-35, enables: tb2-approval-step, link: "[[jira/tickets/CCC-35|CCC-35]]" }
  - { idea: callback contract RFC, enables: tb2-approval-step }
path:
  - { ticket: PRD-4, tag: product, link: "[[jira/tickets/PRD-4|PRD-4]]" }
  - { idea: audit trail for approvals }
---
```

Decided:
- Plain keys (`tickets`, `ticket`, `enables`) are the source of truth the app reads; the `link`/`links` wikilink fields are written alongside purely so Obsidian's graph draws the edges. If a human or Claude edits only the keys, the app rewrites the links on its next write (and treats missing links as fine when reading).
- Slugs are generated from titles on create and never change on rename (renaming edits `title` only), so links stay stable.
- Writes follow the existing patterns: atomic writes, one serialised writer per file, front matter edited with body preserved, and a conflict check against the file's mtime (as notes do) so a concurrent Obsidian/Claude edit isn't silently overwritten.
- Watcher maps `plan/**` changes to a new live event `{ type: "plan" }`; the Plan tab re-fetches (with the same render-deferral while an inline editor or drag is active).
- Invalid YAML in a plan file: that file is skipped with a visible warning in the Plan tab; it is never overwritten while broken (same rule as `views.yaml`).

### Jira data for the Plan tab

- On open/refresh, the initiative's tickets are fetched with JQL `parent in (<epic keys>)` plus `key in (<every key referenced in its slices and sprint files>)`, cached in `.cache/plan/<initiative-slug>.json`. Epics themselves are fetched too (for the header and ticket files).
- These tickets join the union that feeds 4a's `jira/tickets/` files.
- The existing refresh interval and manual refresh apply; Jira errors show in the Plan tab like they do on views.
- A referenced key that Jira doesn't return is shown as a muted chip "AAA-999 · not found" (reuse the board's not-found handling).

### Copy for Claude

Copies a markdown summary of the initiative: period, owner, epics; per sprint: each slice (owner, steps with tickets and statuses, flags), lane ② and ③ items. Same clipboard mechanism as existing copy actions. Intended for "propose tracer bullets for sprint 13" or "draft my sprint summary" conversations; Claude then edits the files directly.

## Testing expectations

- 4a: unit tests for ticket-file rendering (links, tags, note/groom presence, changed-only writes, stale deletion), `issuelinks` parsing; an app-level test that a refresh writes the files into a temp `NOTES_DIR`.
- 4b: unit tests for plan parsing/serialising (round-trip preserving bodies and unknown fields), each flag, lane counts, unplaced computation; API tests for each write route including the Host/Origin/Content-Type gates and conflict handling; a Chrome check of the grid against a throwaway server with fake data (as done for column widths).

## Left to the builder

- Route shapes and the client module split (follow existing `api.ts`/`board.ts` patterns).
- Exact palette for slice colours (must read well in all 10 themes; pick from theme tokens if possible).
- How drag-and-drop is implemented (reuse the board/column drag patterns).
- The grid's exact spacing and the empty states' wording (keep generic).

## Settled after the builder check (Claude's calls)

1. **Sprints per ticket.** Extend the Jira parser to keep *all* of a ticket's sprints with their state (`sprints: { name, state }[]`), keeping the existing single `sprint` field (unchanged behaviour for tables). Sprint column state in the Plan header comes from these. **Spill** = a slice ticket that is not Done and whose sprints do not include the slice's sprint but do include a later one of the period. Carry-over from an earlier sprint is not spill. 4a ticket files list all sprints.
2. **What the Plan fetches.** JQL: (`parent in (<epics>)` AND `statusCategory != Done`) OR `key in (<referenced keys>)`. Done children only appear if referenced. The unplaced tray therefore never fills with old closed work, and `jira/tickets/` stays proportionate. Existing pagination and limit handling apply.
3. **The ticket-file union.** After any refresh, the union is recomputed from all caches *on disk*. A failed refresh leaves its old cache in place, so nothing is pruned because of an error. Keys in the not-found state are excluded from the union, so their files are pruned.
4. **Plan writes are operations, not whole-file saves.** Like the board's ops, each UI action (`addStep`, `moveStep`, `attachTicket`, …) is sent as an op and applied by the server to the *current* file under the serialised writer. A concurrent external edit is therefore merged, not rejected. There's no base-mtime conflict for front-matter ops. Body edits in the side drawer use the notes' mtime conflict check.
5. **Delete, rename and move exist in v1, behind a confirm for deletes.** You can delete an initiative (and its slice and sprint files) or a slice, move a slice to another sprint with a select on its header, and remove a lane item. Dangling `enables` references are left in place and flagged ("enables a missing slice"). Moving a slice so an `enables` points backwards gets flagged too, not rewritten.
6. **One ticket in several places is allowed.** It's counted once for a slice's done/total. "Unplaced" means in no step and no lane item of this initiative.
7. **Property collisions in 4a.** Custom column values whose id collides with a reserved property (`key`, `summary`, `status`, `statusCategory`, `type`, `priority`, `assignee`, `sprint`, `sprints`, `labels`, `url`, `parent`, `links`, `tags`) are written as `note_<id>`. Tags are made from single-select and multi-select values, one tag per value.
8. **`plan.yaml` edits preserve comments.** Use `yaml`'s Document API when the UI appends a period. Never rewrite the whole file.

## Calls made by Claude during brainstorming (for the user to check)

- 4a before 4b.
- Sprints per period are listed explicitly in `plan.yaml` (rather than discovered from Jira dates), matched to Jira by exact name.
- A slice lives in exactly one sprint; spill is flagged, not modelled.
- Lane ②/③ live in one file per initiative × sprint.
- Ticket counts (not story points) for the lane-split bar.
- The app does not write Obsidian config; the README suggests graph colour groups.
- `jira/tickets/` mirrors only cached tickets and prunes the rest.
